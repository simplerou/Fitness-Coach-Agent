# 一、总述

## 0.1 场景选取说明

题目要求"结合自己以往的学习工作经历或者个人爱好"构思场景。三个场景分别对应三条个人线索：

| 场景 | 对应经历来源 | 为什么我判断它值得被智能体解决 |
| :--- | :--- | :--- |
| 场景一 合同/制度合规审查 | 工作经历：【请替换为真实经历，例：在 XX 公司参与过合同初审/制度落地，见过业务与合规来回拉扯的过程】 | 【填写：这个痛点为什么真实高频、现有工具为什么没解决】 |
| 场景二 论文/技术文献精读 | 学习经历：【例：读研/转行期间为写综述集中精读过 N 篇文献】 | 【填写】 |
| 场景三 个性化健身/运动规划 | 个人爱好：【例：有 N 年训练经验，用手表/App 记录，踩过模板计划的坑】 | 【填写】 |

带【】的部分需要替换为真实经历。评审关心的是"你为什么选这三个场景"，而不是场景本身描述得多细。

**三个场景共同满足的选取标准**：

1. **痛点高频且代价可量化**——不是"有点麻烦"，而是"每周消耗 X 小时"或"漏掉会造成 Y 损失"

2. **知识密集型**——核心能力是"在海量专有知识里找依据并给出判断"，这正是 LLM + 检索的强项

3. **错误有明确兜底人**——合规岗、使用者本人、用户自己，智能体不承担最终决策

4. **我能判断它答得对不对**——否则无法设计评测集，也无法验收

## 0.2 三个场景的共性方法论

三个场景表面差别很大，拆到底层是**同一套架构**。这是本次需求分析最重要的一个结论：核心框架做一次，可以复用到三处。

| 层次 | 通用设计 | 场景一 | 场景二 | 场景三 |
| :--- | :--- | :--- | :--- | :--- |
| 知识底座 | 结构化切分 + 元数据（来源/版本/生效日期） | 制度条款、法规 | 论文章节 | 动作库、安全规则 |
| 检索 | 混合检索（关键词 + 向量）+ 重排 | 按合同类型召回制度 | 按问题跨文献召回 | 按目标与状态召回动作 |
| 生成 | **强制引用，无出处不下结论** | 引到制度原文条款 | 引到文献章节页码 | 引到动作库条目 |
| 判定 | **离散三分类 + 置信度**，不输出模糊结论 | 符合 / 存疑 / 违规 | 已涉及 / 结论矛盾 / 未涉及 | 按计划 / 降负荷 / 停止 |
| 兜底 | 低置信度一律转人工，不硬答 | 需人工确认 | 未涉及 | 就医提示 |
| 闭环 | 人工修正回流为评测集 | 合规岗推翻记录 | 用户纠正引用 | 用户反馈不适 |
| 评测 | 固定测试集 + 分层指标 | 历史合同 | 已读文献 | 训练日志回看 |

**可复用的三个技术资产**：

1. 引用溯源框架（段落级定位 + 出处渲染）

2. 三分类判定 + 置信度阈值的调参流程

3. 「人工修正 → 评测集 → 回归测试」的闭环工具链

## 0.3 三场景横向对比

| 维度 | 场景一 合规审查 | 场景二 文献精读 | 场景三 健身规划 |
| :--- | :--- | :--- | :--- |
| 目标用户规模 | 中（一个公司的业务 + 合规） | 小（个人 / 小团队） | 大（大众消费者） |
| 数据敏感度 | **极高**（商业机密 + 合同） | 低（公开文献为主） | **高**（健康数据属敏感个人信息） |
| 数据可得性 | 中（制度库需内部授权） | 高（公开可得） | 低（可穿戴数据受平台限制） |
| 技术难度 | 高（条款级比对、版本管理） | 中（长文分段、跨文检索） | 中高（实时 + 安全规则） |
| 法律/合规风险 | **高**（错误结论致实际损失） | 低（需防学术不端） | **高**（涉医疗边界） |
| 商业价值 | 高（B 端付费意愿强） | 低（个人付费弱） | 中（订阅制，但获客贵） |
| 落地难度 | 高（需嵌入 OA/审批流） | 低（本地工具即可） | 中（需 App + 硬件生态） |
| 建议顺序 | 次做（痛点深、价值高） | **先做**（数据公开、无合规风险，最快跑通引用溯源框架） | 最后做（法律与数据门槛最高） |

**组合逻辑**：场景二作为**技术验证**跑通框架，场景一作为**价值落地**（复用框架 + B 端付费），场景三作为**探索**（需额外解决法律与硬件问题）。

# 二、个性化健身/运动规划智能体

## 3.1 背景与痛点

**典型现状**：有运动基础的爱好者用 App 记录，但计划靠模板或感觉：

- 模板不考虑你的恢复状态，状态差也照练

- 计划不会因进步自动调整

- 动作不标准没人纠

- 饮食恢复建议割裂

- 受伤了才知道练过头

**痛点拆解**：

| 痛点       | 表现                | 代价             |
| :--------- | :------------------ | :--------------- |
| 计划僵化   | 模板不因人因时变    | 练了没效果或过度 |
| 状态被忽略 | 睡眠差/心率高仍照练 | 受伤、疲劳累积   |
| 反馈滞后   | 练完才知道不对      | 错误动作固化     |
| 数据孤岛   | 运动/饮食/睡眠分开  | 看不到全局       |
| 缺解释     | 不知道为什么这么练  | 不信任、不坚持   |

## 3.2 用户画像

| 角色                 | 诉求             | 频率 | 特征           |
| :------------------- | :--------------- | :--- | :------------- |
| 健身爱好者（主用户） | 系统提升，别受伤 | 每天 | 有基础，愿记录 |
| 跑步/骑行爱好者      | 备赛，科学训练   | 每天 | 关注数据       |
| 减脂人群             | 可持续、不反弹   | 每天 | 需鼓励         |
| 康复期用户           | 安全恢复         | 每周 | 需医疗边界     |

## 3.3 用户旅程

1. **建档**：填目标、基础、伤病史、可用器械、时间

2. **接入**：阶段一通过网页手动录入训练与状态数据；设备同步作为后续评估项

3. **生成计划**：智能体出周计划，解释设计逻辑

4. **每日执行**：当天看状态（睡眠/心率/RPE），智能体调整强度

5. **训练中**：动作示范 + 纠错提示

6. **训练后**：记录 RPE，反馈调整

7. **周期复盘**：进步曲线 + 瓶颈分析 + 下周期计划

8. **联动**：饮食/恢复建议随训练量变

## 3.4 功能需求

**P0**

- **F1 建档与目标设定**：目标、基础、伤病、器械、时间

- **F2 数据接入**：阶段一支持手动录入训练、RPE、主观感受、睡眠与静息心率，并记录来源、日期和缺失状态；后续再评估设备同步

- **F3 周计划生成**：基于目标 + 历史 + 恢复，生成并解释

- **F4 每日动态调整**：根据当日状态调强度，说明为什么

- **F5 安全边界**：不适/伤病信号触发"停止+就医"提示

- **F6 统一数据视图**：把训练量、睡眠、静息心率、主观感受汇总在一处呈现（对应 3.1 中"数据孤岛"痛点，P0 阶段至少要做到"看得到全局"，跨维度**建议联动**放 P1）

**P1**

- **F7 动作库与纠错**：视频示范 + 常见错误提示

- **F8 周期复盘**：进步曲线、瓶颈、下周期建议

- **F9 饮食恢复联动**：按训练量给建议

**P2**

- **F10 社群/打卡**：激励与陪伴

- **F11 赛事计划**：针对具体比赛做周期化训练

## 3.5 非功能需求

| 维度   | 要求                           |
| :----- | :----------------------------- |
| 安全   | 涉及健康，必须有就医提示与免责 |
| 可解释 | 每次调整说明原因               |
| 个性化 | 计划随数据持续更新             |
| 实时   | 当日调整 < 5 秒响应            |
| 隐私   | 健康数据加密，用户可删         |
| 依从性 | 计划执行率提升                 |

## 3.6 数据与工具

- **数据源**：阶段一为用户手动输入和动作库；可穿戴设备、运动 App 数据属于后续接入评估

- **工具**：数据接入 API、规则引擎（安全边界）、LLM（计划生成与解释）、视频库

- **安全规则**：硬编码的"红线"（胸痛、眩晕、关节剧痛 → 停止并就医）

## 3.7 边界与风险

| 风险         | 应对                                 |
| :----------- | :----------------------------------- |
| 带伤硬练     | 伤病史建档 + 每日状态问询 + 红线拦截 |
| 过度训练     | 负荷监控 + 强制降负荷日              |
| 健康建议越界 | 明确"非医疗建议"，异常转就医         |
| 数据不准     | 多源交叉验证，异常值提示             |
| 用户不信任   | 每次调整给解释                       |
| **法律合规** | 健康数据属敏感个人信息，需单独同意；免责声明**不能**免除因建议不当造成的侵权责任。MVP 限自用/小范围内测，不对外公开发布 |
| **数据可得性** | 可穿戴平台的数据开放程度差异大，需提前实测可获取的字段与延迟 |

## 3.8 验收指标（含测量方法）

| 指标 | 目标值 | 测量方式 | 时间点 |
| :--- | :--- | :--- | :--- |
| 计划执行率 | 提升 ≥ 20%（对比模板组） | A/B 对照，两组各 ≥ 30 人，统计 4 周完成率 | 上线后 4 周 |
| **ACWR 超标次数** | 不高于对照组 | 计算急慢性负荷比，统计超出安全区间的天数 | 持续 |
| 强制降负荷触发率 | 有触发且用户接受率 ≥ 70% | 埋点统计触发次数 + 用户是否采纳 | 持续 |
| 过度疲劳事件 | 不增加 | 用户主动上报"异常疲劳"的次数 | 持续 |
| **受伤事件** | 不增加 | 用户上报。**注意：受伤是低频事件，小样本无法统计显著，故此指标只作观察，不设硬性统计承诺** | 长期观察 |
| 计划可解释性 | ≥ 80% 用户能说清"为什么这么练" | 问卷 + 让用户复述计划理由，人工评分 | 上线后 4 周 |
| 4 周留存率 | 提升（**北极星指标**） | 产品埋点 | 持续 |
| 每次调整响应 | < 5 秒 | 端到端埋点 | 持续 |

**为什么把"受伤事件不增加"降级**：受伤是低频事件，要检出统计显著差异需要极大样本，小规模验证根本测不出来。改为可观测的代理指标（ACWR 超标次数、强制降负荷触发率、执行率），这些能在几十人的样本里看出趋势。

## 3.9 MVP 范围

**做**：建档、数据接入、统一数据视图、周计划、每日调整、安全边界。

**不做**：动作纠错、饮食联动、社群、赛事计划。

## 3.10 AI 协作提示词

"帮我做健身规划智能体的需求分析。用户是有基础的爱好者。请：1）列出 5 个必须由用户确认而非自动决定的节点；2）设计'状态差时降负荷'的判断逻辑（输入、规则、输出）；3）写出安全免责与就医提示的触发条件；4）给出 MVP 清单和验收指标。"

## 3.11 AI 协作过程与人工修正记录

| # | 我让 AI 做什么 | AI 的输出 | 我发现的问题 | 我的修正 |
| :--- | :--- | :--- | :--- | :--- |
| 1 | 列必须由用户确认而非自动决定的节点 | 列了目标设定、伤病情况 | 漏了"计划变更"——自动改计划而不告知会让用户困惑、失去掌控感 | 补入：任何周计划调整必须给出变更说明，用户可一键回退 |
| 2 | 设计"状态差时降负荷"的判断逻辑 | 给了心率阈值规则 | 单靠心率不可靠（手表误差大、个体基线差异大） | 改为多信号投票（睡眠 / 静息心率偏离基线 / RPE / 主观感受），且**判定就低不就高** |
| 3 | 写安全免责与就医提示的触发条件 | 胸痛、眩晕、关节剧痛 | 漏了"渐进性异常"——不是急性症状但持续恶化的情况 | 补：连续 3 天静息心率显著高于基线，或训练表现持续下降 → 建议休息并咨询医生 |
| 4 | 给验收指标 | 采用"受伤事件不增加" | 受伤是低频事件，小样本测不出统计显著 | 改为代理指标：ACWR 超标次数、强制降负荷触发率、执行率（见 3.8） |
| 5 | 分析法律边界 | "加个免责声明即可" | 健康数据属敏感个人信息需单独同意；且免责声明不能免除因建议不当造成的侵权 | 明确 MVP 限自用/小范围内测，不对外发布；若发布需专门法律评估（见 3.7） |
| 6 | 梳理痛点与功能的对应关系 | 痛点列了"数据孤岛" | P0 阶段 F2 只解决接入，跨维度联动 F8/F9 全在 P1——P0 交付后痛点并未解决 | 在 P0 增加 F6 统一数据视图，联动仍留 P1 |

## 3.12 替代方案对比

| 方案 | 能力 | 不足 |
| :--- | :--- | :--- |
| 通用训练模板 / 网上课表 | 免费、简单 | 不因人、不因时 |
| Garmin Coach / TrainingPeaks | 已有动态调整，背靠硬件与教练体系 | 绑定特定硬件生态；解释性弱；不覆盖力量训练的动作层 |
| Whoop | 恢复度监测领先 | 侧重回答"该不该练"，不解决"练什么" |
| Keep / 各类健身 App | 内容多、上手门槛低 | 计划僵化、不做跨维度联动 |
| **本方案** | 不绑定硬件，以**"解释为什么"**和**"跨维度联动（训练 + 睡眠 + 饮食）"**为核心 | — |

**诚实的判断**：如果用户已在 Garmin/Whoop 生态内，本方案增量有限。**真正的差异化人群是"用普通手表/手机、力量与有氧混合训练、需要有人解释计划逻辑"的中间用户。** 这个定位需要进一步验证。

## 3.13 未验证假设清单

| # | 假设 | 若不成立的影响 | 验证方式 | 状态 |
| :--- | :--- | :--- | :--- | :--- |
| 1 | 后续能通过 Apple Health / Android 官方健康数据路径获取所需字段 | 影响未来自动同步能力，不影响手动数据 MVP | 目标客户端确定后，实测字段、权限与延迟 | 后续阶段验证 |
| 2 | 用户愿意每天记录 RPE 和主观感受 | 状态判断只剩被动数据，准确度下降 | 观察 2 周记录率 | 待验证 |
| 3 | 手表心率数据足够可靠，可用于降负荷判断 | 误判导致该练不练、该停不停 | 与用户主观感受交叉验证 | 待验证 |
| 4 | 用户能理解并接受"今天降负荷" | 觉得是敷衍，执行率反而下降 | 可用性测试 | 待验证 |
| 5 | 非医疗器械定位不构成合规问题 | 上架/发布受阻 | 法律咨询 | 待验证 |

## 3.14 成本与收益

| 项 | 估算 |
| :--- | :--- |
| 周计划生成 | 约 1 万 token / 次 |
| 每日调整 | 约 0.2 万 token / 次 |
| 周期复盘 | 每月一次，成本可忽略 |
| **推理成本合计** | **单用户年成本约 30~60 元（按主流模型价格估算）** |

**收益**：若采用订阅制（参考同类产品 15~30 元/月的区间），推理成本占比可控。

**关键结论**：推理成本不是瓶颈，**留存率**才是，且**获客成本远高于推理成本**。因此 3.8 中"4 周留存率"应作为北极星指标，而不是计划执行率。

## 3.15 集成与落地路径

| 阶段 | 形态 |
| :--- | :--- |
| 一（MVP） | 响应式 Web 网页，桌面与移动浏览器均可使用；训练、RPE、主观感受、睡眠和静息心率以手动录入为主，不依赖手机传感器或平台同步 |
| 二 | 根据 MVP 用户反馈评估是否增加微信小程序；验证登录、数据授权、隐私流程和维护成本 |
| 三 | 若自动健康数据接入有明确价值，针对选定客户端验证 Apple Health / Android 官方健康数据路径及设备覆盖 |
| 四 | 评估厂商开放平台及健身房 / 教练协作模式 |

阶段一的 Web 网页无法默认读取微信运动或系统健康数据，因此步数不属于 MVP 输入。后续是否开发小程序或原生客户端，由试点使用情况、目标用户分布和平台能力共同决定；平台字段、授权方式与数据延迟须实测，不能把计划集成写成已具备能力。
## 3.16 冷启动与失败兜底

| 场景 | 处理 |
| :--- | :--- |
| 新用户无历史数据 | 第一周设为**基线周**：按保守负荷执行，同时采集基线，不生成激进计划 |
| 用户不戴手表 | 降级为主观 RPE + 训练日志驱动，并明确告知精度下降 |
| 数据异常（静息心率突高 / 睡眠数据缺失） | 不据此下结论，提示"数据异常，请确认" |
| 用户连续 7 天未执行 | 不指责，主动询问原因并调整计划难度 |
| 触发安全红线 | 停止该次训练建议，给出就医提示，并**停止后续自动加负荷**直到用户确认恢复 |

## 3.17 与人类教练 / 医疗的角色关系

- **不是医生**：任何症状类问题一律转就医，不给诊断

- **不是教练的替代**：定位为"训练助理"，可向教练输出执行数据

- **可协作**：预留"教练 / 康复师批注"接口，让专业人士的意见可以覆盖 AI 建议（**专业人士意见优先级高于 AI**）

## 3.18 反馈闭环与迭代机制

- 每次训练后收集两项：实际完成度 + 主观难度（RPE）

- **"没按计划练"必问原因**（没时间 / 太累 / 不喜欢 / 受伤）——不同原因触发完全不同的调整策略

- 受伤或不适事件为最高优先级，立即回溯最近 14 天的计划与负荷

- 每月统计：强制降负荷触发率、ACWR 超标次数、执行率趋势

- **责任边界**：用户可自行覆盖 AI 建议，覆盖行为留痕；连续覆盖 3 次后主动询问是否调整长期计划
