# fitness-coach-agent 项目规划（手动数据优先 + 多信号降负荷 + 安全规则先行）

> 依据《Agent—个性化健身运动规划业务需求设计》v1.2　　**当前版本**：V1.1.0 本机可运行基础版；浏览器原生页面 + FastAPI + 本机 PostgreSQL，每日状态与训练日志持久化，安全暂停与计划仍暂存内存。　　**目标范围**：响应式 Web 网页；账号体系、完整安全状态持久化及设备接入按后续版本逐步加入。　　**规划书版本**：v1.4（补充 V1 技术取舍与迭代策略）

## 项目背景与主要功能

### 项目背景

健身爱好者通常需要在固定训练计划、当天身体感受和长期训练目标之间自行权衡。计划缺少对训练记录、主观疲劳、恢复情况和伤病禁忌的连续参考时，用户难以判断当天是否应按计划训练、降低负荷或暂停；计划调整的理由不清楚，也会降低用户对建议的信任与执行意愿。

本项目面向有训练基础、愿意记录的健身爱好者，提供训练计划和日常调整辅助。系统结合用户目标、训练日志、RPE、主观感受及用户可提供的恢复信息，给出有理由、可回退的建议。阶段一以手动记录和小范围内测验证核心流程，不把未验证的可穿戴数据接入作为前提；安全筛查与确定性规则优先于生成式模型。

### 项目主要功能

1. **用户建档与目标设置**：记录训练基础、目标、可用时间、器械条件及伤病/禁忌，作为计划与动作筛选依据。
2. **训练记录与状态查看**：记录训练内容、时长、RPE、完成度和未完成原因；查看记录来源、日期及缺失状态。睡眠、静息心率可手动提供或标记缺失；阶段一不依赖自动步数采集。
3. **个性化周计划**：根据目标、训练基础、时间安排和动作禁忌生成保守计划，并说明安排理由；阶段一未授权外部模型时使用本地模板。
4. **每日训练建议与调整**：根据有效的训练和主观状态信号，给出按计划、降低负荷或信息不足等结果，并展示影响决策的原因；数据缺失不会被当作状态正常。
5. **安全筛查与暂停处理**：每日先进行结构化症状筛查；命中红线时停止生成训练建议并持久化暂停状态。满足相应恢复确认后才解除暂停，模型不能绕过安全门禁。
6. **计划变更、回退与隐私管理**：告知计划调整理由，支持一键回退；用户可查看、撤回授权并申请删除健康数据。可穿戴自动同步、动作视频纠错和饮食联动不属于阶段一核心交付。

## 0. 本版范围、前提与阶段门

本规划将阶段一客户端确定为响应式 Web 网页。网页 MVP 仅依赖用户手动录入，不要求读取手机传感器、微信运动或可穿戴平台数据；小程序、系统健康数据和厂商设备接入均作为后续独立评估项，不阻塞 MVP。

| 项目 | 阶段一 MVP 决定 | 后续阶段 |
| :--- | :--- | :--- |
| 用户 | 有训练基础、愿意记录的健身爱好者；仅邀请制小范围内测 | 通过试点确认后再评估公开发布及其他人群 |
| 必要输入 | 目标、伤病/禁忌、训练记录、RPE、主观感受；睡眠与静息心率可手动填写或标记缺失 | 评估 Apple Health / Android 平台字段、权限、同步延迟后再接入 |
| 可选输入 | 阶段一无自动采集输入；支持手动补充睡眠与静息心率 | 评估小程序、原生应用或平台 API 的可行性后再接入 |
| 核心交付 | 保守周计划、每日规则建议、调整解释与回退、健康数据查看/删除、红线流程 | 动作视频纠错、饮食联动、社群、赛事计划均不在 MVP |
| 发布边界 | 仅自用/小范围内测；上线前完成人工安全规则审阅、授权和数据删除验证 | 公开发布前重新进行法律、平台和安全评估 |

**阶段门**：MVP 使用响应式网页和手动数据验证建档、计划、调整与解释；任何缺失的睡眠/心率字段都显示“未提供”，不能当作正常值。平台自动同步未完成真实验证前，不宣传自动采集或基于设备数据的个性化效果。

**估算口径**：第 13 章为工程人日初估，假设一名熟悉所选技术栈的工程师可连续投入，测试样本、设备/账号和开发者资质可及时提供；不含业务招募、专业人士审阅、法律咨询及平台审核等待。条件不满足时先补条件或调整范围，不把表中天数作为交付承诺。

## 1. 一句话定位

一个面向健身爱好者的个性化训练助理：用户建档并记录训练、RPE、主观感受，以及可提供的睡眠/静息心率；系统生成带理由的周计划，并按可用信号给出每日建议。急性症状由确定性安全流程拦截，模型不得给出继续训练建议或诊断。阶段一以手动记录为主，可穿戴自动同步属于后续验证与集成。

它的自我定位是 **训练助理**，不是医生，也不是教练的替代：

- 症状类问题一律转就医，不给诊断（3.17）

- 每次调整强度都必须给出理由，用户可一键回退（3.11 修正 #1）

- 预留教练 / 康复师批注接口，**专业人士意见优先级高于 AI**（3.17）

一件事的结构长这样：

```
用户手动记录 / 可选手机步数 ──> 数据接入层 ──> 训练状态信号
                                 │
                     ┌───────────┼────────────┐
                     ▼           ▼            ▼
                安全红线引擎   多信号投票   计划生成 LLM
                (硬编码规则)  (就低不就高) (解释设计逻辑)
                     │           │            │
                     └───────────┴────────────┘
                                 ▼
                       今日建议 + 为什么 + 可回退
```

> 把"红线"和"投票"拆成两个独立组件，是这份规划里最先确定、也最不肯让步的一条：红线要的是**确定性**（命中即停，不问模型），投票要的是**保守性**（信号冲突时取更低的负荷档）。两者都不属于 LLM 的自由发挥范围——阶段一的日常决策与理由由本地规则/模板负责；周计划模型只有在单独授权后才参与文案生成。

## 2. 为什么是「多信号融合 + 每日动态调整」这个组合

这个组合不是从技术出发选的，是被两个已发生的失败逼出来的。

第一个失败是**单信号**。需求文档 3.11 的修正记录 #2 指出心率阈值不可靠，因此采用多信号综合判断。但阶段一不假定能自动拿到手表数据：睡眠、静息心率、RPE、主观感受均记录来源、时间和缺失状态；只使用用户确实提供且通过基本校验的输入。可用信号不足时，系统应降低判断强度并明确提示，不能用缺失数据补出“正常”。

第二个失败是**模板计划**。3.1 的痛点表第一条就是"计划僵化：模板不因人因时变"，代价是"练了没效果或过度"。静态课表无论多科学，都回答不了"我昨晚只睡 4 小时，今天还照原计划冲大重量吗"。

两个失败合起来指向同一个设计：**判断要多个证据一起看（融合），结论要每天重算（动态）**。

| 信号 | 单独用会怎样 | 融合后承担什么角色 |
| :--- | :--- | :--- |
| 静息心率偏离基线 | 手表误差 + 个体基线差异，误判高 | 有连续、可比较的数据时作为趋势提示；未经专业审阅的数值阈值不作为诊断或自动停训依据 |
| 睡眠时长 / 分期 | 单晚波动大，一天睡差不能说明问题 | 弱信号：够一票，不够否决 |
| 昨日 RPE | 用户可能虚报或高估 | 弱信号：与客观数据交叉验证 |
| 主观感受 | 完全主观，无基线 | 弱信号，但权重高——用户说难受就是难受 |
| ACWR（负荷比） | 依赖完整、连续的训练记录，解释有局限 | 数据充足后作为负荷观察项；候选阈值需验证，不作为受伤预测或医学安全线 |

> **为什么采用规则 + 生成式计划**：规则负责安全边界与每日调整，本地模板给出具体原因；周计划的自然语言组织可由经授权的模型辅助，但模型不能决定安全档位或突破本地禁忌。

> **为什么不用纯 LLM**：让模型每天读一堆心率数字自由发挥要不要降负荷，等于把安全边界交给一个概率模型。红线必须是 `if` 语句，这是不可协商的（见 9.1）。

## 3. 场景设定：健身爱好者（可一键换成别的运动人群）

默认场景是 **有训练基础的健身爱好者**（3.2 主用户）：愿记录、想系统提升、最怕受伤。系统能力的默认权重也按这个人群调——力量与有氧混合、每周 3~5 练、用普通手表或手机。

要换成别的运动人群，只需替换三样东西，架构一行不改：

- **画像模板**（`user_profile.goal/level`）—— 换成跑步/骑行备赛（3.2）、减脂人群（3.2）、康复期用户（3.2）

- **规则配置**（经审阅后启用的安全规则与训练负荷策略）—— 不同人群的规则需重新验证，不能只改一个阈值就视为适配

- **动作库子集**（`exercise` 的 `pattern` 过滤）—— 跑步人群主用有氧与力量辅助动作

### 3.1 典型问题（用于验收用例设计）

以下是用于设计验收用例的典型问题；期望路径会明确处理输入缺失和规则未启用的情形：

| 难度 | 问法 | 期望走的路径 |
| :--- | :--- | :--- |
| 简单 | "帮我出一份下周的三练计划" | 建档数据 + 动作库检索 → 计划生成 → 附解释，不触发任何红线 |
| 简单 | "我昨天 RPE 7，今天该练什么？" | 读昨日日志并询问今日感受；单一 RPE 不自动判定状态差，信号不足时说明信息不足并给出保守基础选项 |
| 中等 | "我昨晚只睡 5 小时，今天还练腿吗？" | 只使用用户确实填写且有效的睡眠/心率/主观信号；缺失字段显示未知，依据可用信号决定是否调整 |
| 中等 | "这周我已经连练 6 天了，负荷是不是太高？" | 记录不足 28 天时说明无法计算 ACWR；记录充分且规则经审阅后，展示负荷趋势提示而非受伤结论 |
| **困难** | "连续几天静息心率高于我平时，我还能加重量吗？" | 仅当连续数据有效且趋势规则已专业审阅启用时，给出保守休息提示并暂停自动加负荷；不作诊断 |
| **陷阱** | "我胸口有点闷，今天还能练腿吗？" | **必须被安全红线拦住**：不生成训练建议，直接提示停止并就医 |

> 陷阱题是**硬指标**：这条如果没被拦住（哪怕答得再"贴心"），整个系统不合格。理由见 15 章的"安全红线拦截率 100%"。验收时这条要单独拿出来反复跑，不能只跑一次。

## 5. 技术栈与环境

### 后端 Python（容器 `api` 与 `worker`）

```
Python 3.11
fastapi + uvicorn[standard]        # API 层，长连接与 SSE
langgraph >= 0.2                   # 计划生成 / 每日调整的状态机
langchain-core + langchain-openai  # 走 DashScope 兼容模式（base_url 指向百炼）
pydantic >= 2.6                    # 请求体与"信号结构体"的校验
pydantic-settings                  # 环境变量集中管理
sqlalchemy >= 2.0 + asyncpg        # PostgreSQL 异步驱动
alembic                            # 表结构迁移（健康数据表改不得）
redis[hiredis]                     # 缓存 + 限流计数 + Celery broker
celery >= 5.3 + celery beat        # 每日批量生成；平台同步仅后续启用
httpx + tenacity                   # 后续平台接入再启用；带重试与限流
PyJWT                              # 会话令牌
```

### 数据层

```
PostgreSQL 16                      # 存用户授权的日状态与训练日志；后续可加 pgvector
Redis 7                            # 热点缓存（基线、今日建议）+ 计数器
```

> 为什么是 PostgreSQL 而不是 MySQL：可穿戴平台的原始回包结构各家不同、随时会变，`JSONB` 能先原样存下、事后再算（schema 不必追着平台改）；同时 ACWR 这类窗口聚合用窗口函数写起来更短。`daily_load` 的 7 天/28 天滚动量就是一行 `ROWS BETWEEN`。

## 6. 分层结构

自顶向下六层，其中**决策层独立于编排层**——这是和"把一切都塞进 Agent"最不一样的地方：

| 层 | 落在哪里 | 职责 |
| :--- | :--- | :--- |
| 1. 展示层 | 响应式 Web（V1 原生 HTML/CSS/JS） | 今日卡片、周计划、解释、RPE 录入、安全筛查 |
| 2. 接入层 | FastAPI（`api`） | 建档、授权/隐私、计划、今日建议、训练记录、安全筛查、每日信号与教练批注接口 |
| 3. 编排层 | LangGraph（`api`/`worker`） | 周计划流程（可选调用已授权模型）；每日调整只读数据并调用本地规则/模板 |
| 4. 决策层 | 纯 Python（**不调 LLM**） | 安全红线引擎 + 多信号投票引擎，确定性输入输出 |
| 5. 工具层 | Python | 动作库检索、ACWR 描述性统计；外部数据适配器仅在对应阶段启用 |
| 6. 数据层 | PostgreSQL + Redis | 档案/日志/派生指标/原始 payload；Redis 扛热点与队列 |
| 观测 | 结构化日志 + 埋点 | 每次降负荷、每次红线命中都留痕，供 15 章指标复盘 |

> **第 4 层必须独立**，不能并进第 3 层。红线与投票是"纯函数 + 数据库读"，而编排层是"可能失败、可能被模型带偏"的环节。把决策塞进编排，等于把安全边界建在一个会抖动的东西上面。

## 7. 数据设计

PostgreSQL 16，库名 `fitness`。下面五组表覆盖 MVP 全部数据需求。

### 7.1 用户档案与伤病史

伤病史不是可选字段——3.7 的第一条风险对策就是"伤病史建档"，它是红线之外的**第二道个性化安全网**（例如膝关节有慢性伤 → 动作库里所有 `pattern=蹲` 的高冲击动作直接屏蔽）。

```
CREATE TABLE user_profile (
    id              BIGSERIAL PRIMARY KEY,
    open_id         TEXT UNIQUE NOT NULL,        -- 微信 openid
    goal            TEXT NOT NULL,               -- 增肌/减脂/备赛/保持
    level           TEXT NOT NULL,               -- 有基础/进阶
    equipment       TEXT[],                      -- 可用器械
    weekly_days     SMALLINT NOT NULL,           -- 每周可训练天数
    session_minutes SMALLINT NOT NULL,
    baseline_ready  BOOLEAN NOT NULL DEFAULT FALSE,  -- 基线周是否已完成
    consent_version TEXT,                        -- 健康数据单独同意版本
    external_model_consent_version TEXT,        -- 第三方模型处理单独授权；NULL = 未授权
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE injury_history (
    id          BIGSERIAL PRIMARY KEY,
    user_id     BIGINT NOT NULL REFERENCES user_profile(id),
    area        TEXT NOT NULL,        -- 部位：膝/腰/肩/踝...
    description TEXT NOT NULL,
    status      TEXT NOT NULL,        -- 已痊愈/恢复期/慢性
    avoid_moves TEXT[],               -- 需规避的动作 id 列表
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 安全红线产生的暂停状态必须持久化，不能只放在当日缓存中。
CREATE TABLE safety_hold (
    user_id             BIGINT PRIMARY KEY REFERENCES user_profile(id) ON DELETE CASCADE,
    hold_kind           TEXT NOT NULL, -- acute_symptom / progressive_notice
    trigger_code        TEXT NOT NULL,
    triggered_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    rule_version        TEXT NOT NULL,
    user_confirmed_at   TIMESTAMPTZ  -- 用户自述已恢复/已完成后续确认；非医疗验证
);
```

### 7.2 每日状态数据、来源与缺失处理

**这是整个项目最关键的一张表，因为它决定了每日调整有哪些可信输入。阶段一不要求自动采集恢复数据。**

| 字段 | 阶段一来源 | 粒度 | MVP 是否必需 | 缺失处理 |
| :--- | :--- | :--- | :--- | :--- |
| 训练记录 / 时长 | 用户训练后录入 | 每次训练 | **必需** | 未记录时不计算该次负荷，提示补录 |
| RPE、主观感受 | 用户训练后 / 当日录入 | 每次训练 / 每日 | **必需**（至少提供其中一项用于 MVP 调整） | 缺失即标记未知，不视为状态良好 |
| `sleep_minutes` 睡眠时长 | 用户手动录入；后续可评估平台同步 | 日 | 可选 | 不参与当日投票；今日卡片显示“未提供” |
| `resting_hr` 静息心率 | 用户手动录入；后续可评估平台同步 | 日聚合 | 可选 | 不参与基线比较；不生成趋势结论 |
| `steps` 步数 | 阶段一不采集；未来平台接入经验证后 | 日聚合 | 非 MVP | 缺失不影响计划与安全判定 |
| `deep_sleep_min` / `hrv_ms` | 阶段二候选平台 | 日聚合 | 不属于 MVP | 未验证前不进入规则 |

> 阶段一以用户主动记录为准，阶段二才评估 HealthKit / Android 平台提供的聚合字段、权限和同步延迟。字段记录必须包含来源、采集时间和有效性；过期、异常或缺失值不进入投票。阶段一 `daily_signal` 仅接收手动来源，`source` 必须准确标为 `manual`；不得从字段值推断来源。

```
CREATE TABLE daily_signal (
    user_id        BIGINT NOT NULL REFERENCES user_profile(id),
    day            DATE NOT NULL,
    source         TEXT NOT NULL,     -- manual/wechat/apple_health/android 等
    resting_hr     SMALLINT,          -- 聚合静息心率 bpm
    hrv_ms         SMALLINT,
    sleep_minutes  SMALLINT,
    deep_sleep_min SMALLINT,
    steps          INTEGER,
    raw_payload    JSONB,             -- 可选的最小必要原始字段；避免无必要长期留存整包
    synced_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (user_id, day, source)
);
```

### 7.3 训练日志与 RPE

3.18 要求"每次训练后收集两项：实际完成度 + 主观难度"，并且"没按计划练必问原因"。所以 `skip_reason` 是**强制选项**，不是自由文本：

```
CREATE TABLE training_log (
    id           BIGSERIAL PRIMARY KEY,
    user_id      BIGINT NOT NULL,
    plan_item_id BIGINT,             -- 关联当日计划条目
    day          DATE NOT NULL,
    completed    BOOLEAN NOT NULL,   -- 实际完成度：是/否
    rpe          SMALLINT,           -- 1~10 主观难度
    feel         TEXT,               -- 精神好/疲劳/酸痛/差（主观感受信号源）
    skip_reason  TEXT,               -- 没时间/太累/不喜欢/受伤
    duration_min SMALLINT,           -- 实际训练分钟数，ACWR 用实测时长而非计划时长
    note         TEXT,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

> **"没按计划练"的不同原因触发完全不同的策略**（3.18）：没时间 → 缩短单次时长；太累 → 降负荷；不喜欢 → 换动作；受伤 → 走红线流程并回溯最近 14 天计划与负荷。用一个字段区分四类处置，是"低成本高回报"的典型。

### 7.4 动作库

动作库是 RAG 的知识底座（对应总述 0.2 的"知识底座：动作库、安全规则"），也是 `avoid_moves` 的匹配对象。

```
CREATE TABLE exercise (
    id                BIGSERIAL PRIMARY KEY,
    name              TEXT NOT NULL,
    pattern           TEXT NOT NULL,      -- 推/拉/蹲/铰链/核心/有氧
    equipment         TEXT,               -- 杠铃/哑铃/自重/器械
    muscles           TEXT[],
    contraindications TEXT[],             -- 禁忌部位，与 injury_history.area 匹配
    difficulty        SMALLINT,           -- 1~5
    media_url         TEXT,               -- P1 视频示范预留
    safety_notes      TEXT,
    embedding         VECTOR(1024)        -- 可选：pgvector，MVP 可先用关键词过滤
);
```

### 7.5 ACWR 等派生指标

ACWR（急慢性负荷比）在本项目中仅作为需求文档要求的**描述性负荷指标**：近 7 天训练负荷 ÷ 近 28 天平均周负荷；单次负荷用 **sRPE = RPE × 训练分钟数**。该指标受记录完整度、窗口定义和算法选择影响，研究解释也有限；它不是个体受伤概率或医疗安全线。

```
CREATE TABLE daily_load (
    user_id      BIGINT NOT NULL,
    day          DATE NOT NULL,
    day_status   TEXT NOT NULL,           -- trained / confirmed_rest / unreported
    session_load NUMERIC(8,1),            -- trained 时为实际 sRPE；确认休息为 0；未记录为 NULL
    acute_7d     NUMERIC(8,1),            -- 近 7 天负荷总和
    chronic_28d  NUMERIC(8,1),            -- 近 28 天平均 × 7
    acwr         NUMERIC(4,2),            -- acute / chronic
    PRIMARY KEY (user_id, day)
);
```

> **阶段一数据不足时不计算 ACWR**：需具备至少 28 天有效训练日志，缺失日期与零训练必须区分。需求中的 ACWR 对照仅作试点观察；阈值、窗口及对照组口径须在试点方案中预先确定并由专业人士审阅。不能把超出候选区间表述为“预测受伤”或自动触发医疗处置，见 15.4。

## 9. 关键设计决策

这一章是全文精华，别的可以先不看。每条都写清"为什么"和"取舍"。

### 9.1 安全规则先于生成，输入方式不能依赖关键词碰运气

安全检查是确定性门禁，不是 prompt 里的一句叮嘱。阶段一在每日建议前设置结构化症状询问（包括胸痛/胸闷、晕厥/眩晕、严重关节痛、其他明显不适）；用户肯定、无法判断或输入含糊时，不生成训练建议，展示固定的停止与就医提示。自由文本关键词匹配只能作为补充，不能作为唯一识别方式。规则命中后不经过 LLM 润色。

处置分两类，避免把日常状态波动等同于急症：

- **急性症状**：停止本次训练建议，提示尽快寻求医疗评估；暂停自动增加负荷，直到用户确认已获得专业意见并恢复。

- **持续异常提示**：连续静息心率偏高、训练表现下降等仅在数据连续、来源明确时触发保守休息提示，并暂停自动加负荷；它们不是诊断，也不能单独证明需要就医。持续、加重或伴随症状时提示咨询专业人士。

具体症状列表、表述、阈值与处置文案必须在内测前经具备运动健康资质的专业人士审阅并留记录；未完成审阅时，只开放经审阅的结构化急性症状停止流程，不启用未经验证的趋势阈值。免责声明不能替代这项审阅。

> **测试口径**：100% 是指已审阅的结构化安全用例全部触发预期门禁，不代表系统能从任意自然语言中识别所有症状，也不构成临床安全证明。要降低漏报风险，依靠主动询问、模糊输入保守处理、固定提示和人工内测反馈的组合。

### 9.2 多信号投票，且就低不就高

投票引擎只消费通过有效性校验的信号，输出“按计划 / 降负荷 / 暂不生成建议”。急性停止由 9.1 的独立门禁处理。缺失、过期或异常数据是“未知”，不是一张正常票。

| 信号 | 触发条件（示例，实际值在 `rules.yaml`） | 票型 |
| :--- | :--- | :--- |
| 睡眠 | 用户提供且低于个人记录基线 | 候选弱信号；具体规则待内测验证 |
| 静息心率 | 用户提供且连续数据可比 | 趋势提示；未审阅的 bpm 阈值不启用 |
| 昨日 RPE | 有有效训练记录且 ≥ 8 | 候选弱信号 |
| 主观感受 | 用户选择“疲劳/酸痛/差” | 用户不适优先；明显症状转 9.1 门禁 |
| ACWR | ≥28 天训练记录充分后计算 | 描述性负荷提醒；候选上限待验证，不以低值判定过度训练 |

判定规则：

- 急性症状或无法澄清的安全输入 → 由 9.1 门禁停止本次建议

- 弱票 ≥ 2 张 → 降负荷

- 有效状态弱信号 = 1 张 → 软降档（例如减少一档组数/重量）；展示为建议，用户可确认或回退

- **信号互相矛盾时（例如睡眠很好但主观很累）→ 取更保守的那一档**

> **“就低不就高”适用于状态信号冲突，不等于任何单个低质量数值都能触发停训。**候选阈值须先用记录数据和专业审阅验证；信号不足时给出“信息不足，按保守基础计划或暂缓建议”，并说明缺了什么。

### 9.3 降负荷必须给解释——这是用户信任的唯一来源

3.1 的痛点表最后一条："缺解释：不知道为什么这么练 → 不信任、不坚持"。3.5 把"每次调整说明原因"写进了非功能需求，3.8 更是把"计划可解释性 ≥ 80%"做成了验收指标。

所以**每一次调整都必须携带一段解释**，且解释要具体到信号：

```
今日建议减少一档训练量（仅为示例，实际调整由版本化规则确定）

因为：昨晚睡眠 5 小时 10 分（低于你的基线 1 小时 50 分）
      静息心率 62（高于你的基线 8 次）
      → 两个信号同时偏离，属于多信号投票的"降负荷"判定
      今天把深蹲从 5 组降到 3 组，重量维持不变
```

> **解释不是文案，是产品功能**。如果解释每次都只写"今天状态不太好建议减轻"，用户第三次就不看了。可解释性 ≥ 80% 的验收方式（3.8）是"让用户复述计划理由"——这意味着解释必须**可复述**，也就是要引用用户自己能感知的、具体的数字。

> 实现上，解释由本地模板把确定性原因码与用户已知数据渲染成人话；每日解释不调用外部 LLM，不把睡眠、心率、症状、伤病史写入模型请求。

### 9.4 计划变更需告知，且可一键回退

这条来自 3.11 修正 #1——AI 最初只列了"目标设定、伤病情况"需要用户确认，漏掉了**计划变更**。修正结论：**任何周计划调整必须给出变更说明，用户可一键回退**。

落到实现上是三件事：

- 每次生成新计划或调整，都写一条 `plan_change` 记录（改了什么、为什么、依据哪些信号）

- Web 计划页顶部显示"本周计划有 2 处调整"入口

- 每条调整旁有"回退"按钮，回退后该次调整作废并留痕

> **为什么值得单独设计**：用户对"我的计划被悄悄改了"是敏感的。3.13 假设 4 甚至担心"用户能理解并接受降负荷吗，会不会觉得是敷衍以至于执行率下降"。**把控制权交还给用户**，是让降负荷被接受（3.8 要求接受率 ≥ 70%）的关键手段，而不是附带功能。

### 9.5 基线周冷启动，缺少设备数据时降级

新用户没有历史，任何"偏离基线"的判断都无从谈起。3.16 的处置是**第一周设为基线周**：

- 按保守负荷执行，**不生成激进计划**

- 同时采集可获得的训练记录、RPE、主观感受；睡眠和静息心率只有在用户提供且质量可判断时才建立个人参考值

- 基线周结束后 `baseline_ready = TRUE`，投票引擎才开始接管

阶段一所有用户均以**手动记录 + 训练日志驱动**；未提供睡眠/心率时明确告知可用依据和局限，不暗示已读取设备数据。后续接入设备后再按授权与数据质量增加信号。

> **为什么冷启动要单独当一回事**：它决定了产品前 7 天的体验形状。如果第一周就上大负荷，新用户既没数据也没适应性，受伤概率最高、流失率也最高——而 4 周留存是北极星指标（3.14）。用一个"保守的第一周"换"用户活到第四周"，这笔账很清楚。

> **降级路径必须显式告知**，不能静默降级。用户有权知道"你没戴表的这一周，我的判断依据只剩你手动填的 RPE"。

### 9.6 专业意见优先级高于 AI

3.17 明确：预留"教练 / 康复师批注"接口，让专业人士的意见可以**覆盖 AI 建议**，且**专业人士意见优先级高于 AI**。

```
CREATE TABLE coach_annotation (
    id         BIGSERIAL PRIMARY KEY,
    user_id    BIGINT NOT NULL,
    author     TEXT NOT NULL,        -- 教练/康复师标识
    scope      TEXT NOT NULL,        -- 全局/某周计划/某动作
    content    TEXT NOT NULL,
    valid_until DATE,                -- 批注有效期
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

生成计划与每日调整时，`coach_annotation` 中的有效批注作为**最高优先级输入**注入，且 AI 不得推翻——只能执行或标记冲突。

> **这条在架构上意味着什么**：编排层（LLM）之上还有一层人的指令，且这层指令优先。也就是说，"AI 说什么就执行什么"在本项目里是明确不成立的。这也顺带压住了 3.17 的定位风险——**不是教练的替代**，而是给教练输出执行数据的"训练助理"。

### 9.7 健康数据合规，且"免责声明不能免责"

3.7 里最容易被忽略、也最要命的一行：健康数据属敏感个人信息，**需单独同意**；免责声明**不能**免除因建议不当造成的侵权责任。

所以本项目的合规设计不是"加一行免责声明"，而是：

- **单独同意**：在通用隐私政策之外，健康数据（睡眠、心率、伤病史）走**独立的授权弹窗**，且记录 `consent_version` 与授权时间

- **可删**：用户可一键删除全部健康数据（3.5 非功能需求）

- **传输与存储**：客户端到服务端全程 HTTPS；生产凭据不得进入仓库或日志；数据库、备份和导出文件启用受控加密存储，健康字段按最小权限访问。若无法验证备份加密和删除时限，不进入用户内测。

- **撤回与删除**：撤回健康数据授权后停止新的相关采集；删除流程覆盖档案、每日信号、训练日志、派生负荷和队列/缓存副本，并记录删除任务结果。备份按已披露的保留周期到期清除；不能承诺实时从离线备份物理删除时，必须在授权说明中如实写明时限。

- **数据最小化**：默认不保存整份平台原始回包，不把健康数据写入应用日志或分析埋点。阶段一每日决策与解释不调用外部 LLM；症状、心率、睡眠、伤病史不得进入外部模型请求。

- **外部模型边界**：周计划如需调用第三方模型，必须先完成服务商数据处理/留存评估，列明会发送的字段并取得独立、明确的模型处理授权；默认排除姓名、联系方式、症状原文、心率/睡眠数值与伤病史。用户未授权、供应商条款未核实或最小化仍不能满足时，关闭云模型路径，使用本地规则模板或不提供生成式计划。

- **MVP 限自用 / 小范围内测，不对外公开发布**（3.7）——网页可通过受控账号与访问权限开展试用；网页可访问不等于公开发布

- 免责声明照写，但**不当作责任豁免的依据**；产品设计上尽量"少给结论、多给依据"

> **阶段门**：这几项是内测前的核对要求，不代表满足后即可公开发布。公开发布前仍需单独完成法律、平台、健康安全与运营能力评估；免责声明不替代这些工作。

### 9.8 留存优先于功能堆叠

3.14 的关键结论：推理成本不是瓶颈（单用户年 30~60 元），**获客成本远高于推理成本，留存才是瓶颈**，因此 3.8 应把"4 周留存率"而非"计划执行率"作为北极星指标。

这个结论直接改变了排期的取舍：

- 动作库纠错（F7）、饮食联动（F9）、社群（F10）、赛事（F11）全部**不做**——它们不解决"第一周留住人"

- 优先做的是：今日卡片做得准、解释讲得清、降负荷给得出理由、连续 7 天没练会主动问原因不指责（3.16）

> **"少做功能"在这里是产品决策，不是偷懒**。功能每多一个，用户就要多理解一层，第一周的认知负担就多一分；而在北极星是留存的前提下，**降低第一周的理解成本**比增加功能更值钱。

## 10. 前端与交互设计

### 10.1 就四个页面

- **今日**（主页面）：状态卡（红/黄/绿）+ 今日建议 + 为什么 + 一键回退

- **计划**：本周安排、每条动作的说明、"本周有 N 处调整"入口

- **记录**：完成度 + RPE + 主观感受；未完成必选原因

- **安全**：症状上报（胸痛/眩晕/关节剧痛/其他）

### 10.2 今日卡片（整个产品的心脏）

3.4 F6 要求"统一数据视图：把训练量、睡眠、静息心率、主观感受汇总在一处呈现"。今日卡片就是这个视图：

```
┌──────────────────────────────────────┐
│  今天 10/12 周六              ● 黄灯  │
│                                       │
│  建议：按经审阅规则减少一档训练量（界面示意）             │
│                                       │
│  睡眠 5h10m   ↓ 低于基线 1h50m        │
│  静息心率 62  ↑ 高于基线 8            │
│  昨日 RPE 7                           │
│                                       │
│  ▸ 为什么？                            │
│    深蹲 3 组（原 5 组），重量不变      │
│    [ 接受 ]   [ 一键回退原计划 ]       │
│                                       │
│  练完记得回来打分  [ 记录 ]            │
└──────────────────────────────────────┘
```

状态来自规则结果：绿 = 可按计划；黄 = 降负荷建议；灰 = 状态信息不足；橙色提示 = 持续异常趋势（不显示自动加负荷建议）；红 = 命中急性安全门禁（红态下**不显示任何训练建议**，只显示固定安全提示）。所有卡片同时显示每个字段的日期、来源或“未提供”。

> **红态必须"什么都不给"**。如果红态还在旁边放一个"仍想训练"的按钮，红线就等于没有。这一点在 UI 上要写死。

### 10.3 接口契约

前后端只认这七个接口，先写进 README 再并行开工：

```
GET  /api/today        → { level: ask|stop|progressive_notice|insufficient_data|normal|downgrade, plan_items[], reasons[], rollback_token }
POST /api/plan         → { week_plan, explanations[] }
POST /api/log          → { ok }          # 完成度 / RPE / 主观感受 / 未完成原因
POST /api/safety-check → { completed, symptom_status, symptom_codes[] }；命中时写入持久化暂停
POST /api/safety-resolution → { confirmed_recovery, followed_professional_advice? }；急性症状两项均需确认，持续异常确认已恢复
POST /api/daily-signal → { accepted, source, recorded_at, validation_warnings[] }
POST /api/coach-note   → { ok }          # 教练批注（优先级最高）
```

`reasons[]` 是结构化原因数组（哪个信号、偏离多少），前端负责渲染成 10.2 的卡片，**不依赖模型返回的自由文本**；模板解释在网络与模型不可用时仍可显示。

### 10.4 弱网与容错

- 今日建议本地缓存，断网时显示"上次同步于 X"，并明确标注数据可能过期

- RPE 记录先落本地队列，网络恢复后重传（幂等：按 `(user_id, day, plan_item_id)` 去重）

- 提交症状上报时**不允许失败重试吞掉**——红线上报必须成功进服务端，失败要弹"请直接联系医生"兜底文案

## 11. 运行与部署

### 11.1 形态选择：响应式 Web 网页（阶段一）

V1 使用浏览器原生页面，通过桌面和移动浏览器访问；FastAPI 同时托管网页与 JSON API。无需 Node、前端依赖安装或独立静态站点。此版只供本机演示，不开放给真实用户。

阶段一的数据策略：

- 必须支持训练、RPE、主观感受及可选睡眠/静息心率手动录入，并清楚显示来源、日期和缺失状态。
- 阶段一不读取手机传感器、微信运动或可穿戴数据；步数不参与每日安全判断。
- 后续如增加微信小程序、原生应用或健康平台接入，先验证官方能力、权限、隐私流程和维护成本，再单独确定范围。

### 11.2 后端部署（docker-compose）

后续版本再确定生产静态托管与跨域配置。V1 页面和 API 同源运行。

```
services:
  postgres:
    image: postgres:16
    environment:
      POSTGRES_USER: fca
      POSTGRES_PASSWORD: ${PG_PASSWORD}
      POSTGRES_DB: fitness
    volumes: ["pg_data:/var/lib/postgresql/data"]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U fca -d fitness"]
      interval: 5s
      retries: 20

  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    volumes: ["redis_data:/data"]

  api:
    build: ./backend
    command: uvicorn app.main:app --host 0.0.0.0 --port 8000
    env_file: .env
    depends_on:
      postgres: { condition: service_healthy }
      redis:    { condition: service_started }
    ports: ["8000:8000"]

  worker:
    build: ./backend                       # 与 api 同镜像
    command: celery -A app.tasks.celery worker -B -l info
    env_file: .env
    depends_on:
      postgres: { condition: service_healthy }
      redis:    { condition: service_started }

volumes:
  pg_data:
  redis_data:
```

三个要点：

- `worker` 与 `api` **共用镜像、只换 command**，避免两套依赖漂移

- `-B`（beat）与 worker 同进程跑，MVP 阶段够用；规模上来后再拆独立 beat

- `postgres` 用 `pg_isready` 做 healthcheck，`api` 等它 healthy 再起，否则第一次连接必挂

### 11.4 首次上线（内测）检查清单

按顺序过一遍：

- 完成结构化筛查并选择“胸痛”，确认 `/api/safety-check` 返回 `stop`，且此后 `/api/today` **不再给训练建议**

- 未审阅趋势规则保持关闭；规则完成专业审阅后，按规则版本覆盖有效/缺失/异常数据用例

- 点"一键回退"，确认计划回到调整前且留痕

- 删除接口可用：用户能清空全部健康数据及安全暂停状态

- 单独同意弹窗在首次授权健康数据时出现，且 `consent_version` 落库

- 埋点齐全：降负荷触发、红命中、回退、未完成原因都有记录

## 12. 并发与性能

### 12.1 当日调整 < 5 秒怎么做到

3.5 要求"当日调整 < 5 秒响应"。这条每日链路不调用外部 LLM；延迟预算以目标设备的端到端实测为准，而不是靠购买更快的模型：

| 环节 | 目标耗时 | 说明 |
| :--- | :--- | :--- |
| 读今日信号（缓存命中） | < 50 ms | Redis 缓存基线 + 当日手动记录 |
| 红线引擎 | < 5 ms | 纯内存判断 |
| 投票引擎 | < 20 ms | 纯计算 + 少量读库 |
| ACWR（已预计算） | < 10 ms | 凌晨批任务算好，读表即可 |
| 结构化解释模板 | < 50 ms | 不进入外部模型请求 |
| 组装返回 | < 20 ms | —— |
| **预算** | 端到端 P95 < 5 秒 | 目标依赖目标设备与网络实测，不以组件相加代替实测 |

每日建议由安全门禁、确定性规则、数据库读取和模板解释组成，不在关键路径调用外部模型。安全筛查或状态输入更新后使当日缓存失效；缓存只能保存同一规则版本、同一日期且筛查已完成的状态。
### 12.2 每日状态刷新任务编排

Celery beat 的阶段一任务：

- **凌晨 03:30 → `gen_daily`**：基于用户已经提供、且通过质量校验的数据准备当日状态；不把缺失值补成正常，也不调用 LLM 预先生成训练内容。
- 手动录入、完成训练记录或安全筛查变化时，使相应用户当天的缓存失效并按需重算。
- **MVP 不轮询可穿戴平台**。设备接入获批后再单独增加同步任务、授权状态管理、撤回处理和限流策略。

关键约束：

- **按需与可重试**：日批任务只处理有效记录；失败时保留未知状态，不产生默认正常结论。
- **幂等**：同一 `(user_id, day)` 重复计算结果一致，允许安全重试。
- **失败隔离**：单个用户计算失败不影响其他用户；失败原因可查且不泄露健康数据。
### 12.3 限流与超时

- **周计划云模型侧（可选）**：仅对已授权请求设全局信号量与超时；失败转规则模板或提示用户稍后重试，不影响日常安全流程

- **后续平台 API 侧**：只有对应平台集成获批后，才配置指数退避、`Retry-After` 和并发上限；MVP 不轮询外部平台

- **数据库侧**：`asyncpg` 连接池有上限；批任务与在线请求**用不同池**，防止批任务把在线查询排死

- **请求侧**：`/api/today` 端到端 `asyncio.wait_for(..., timeout=5)`，超时返回缓存或降级文案而非报错

### 12.4 后续设备数据同步的性能与可靠性

设备数据同步不在阶段一请求链路中。后续接入时应预期睡眠和静息心率字段可能延迟到晨起后才完整；客户端需展示最近同步时间，延迟/授权失效时保留“未知”，不能沿用旧数据当作今日数据。

平台重复回包通过 `(user_id, day, source)` 幂等键处理。只保存实际需要的字段及数据来源，不默认保留完整原始回包。按用户时区确定日期边界；平台 API 的限流与重试单独测量，不能与 `/api/today` 的 P95 混在一起。

**可穿戴后续探测（不阻塞 M0–M7）**：另安排 3–5 人日做 Apple Health 与当前 Android 官方健康数据路径的技术探针，前提是设备、开发资质和测试账号已到位；如果条件未具备，交付“尚未验证”及所需条件，不以模拟结果替代实测。每个平台记录设备/系统/API 版本、授权方式、字段、延迟、失败情况和样本数。只有数据可用性、用户授权和维护成本达到试点门槛后，才单独估算集成工作。

**并行项**：在 M1 进行期间可先做不依赖自动设备数据的表结构、接口和静态界面；M3 的趋势规则必须等专业审阅，不可因开发排期先行启用。可穿戴适配器不能成为 MVP 阻塞项，也不能用“手动 RPE”伪装成自动同步。

**主要不确定项**：Web 内测的访问控制与健康数据授权流程、删除/备份保留周期、专业规则审阅人是否可用、用户能否持续填写记录。M0 逐项确认负责人和验证方式；任一关键条件未满足，就延后内测或缩小输入与功能范围。

### 14.1 安全规则门禁（独立于 LLM）

```python
# backend/app/decision/redline.py
from dataclasses import dataclass

@dataclass
class SafetyResult:
    action: str       # "ask" | "stop" | "progressive_notice" | "continue"
    reason_code: str | None
    message: str

def check_safety(today, recent, reviewed_rules) -> SafetyResult:
    # 每次给训练建议前必须完成结构化症状筛查。
    if not today.symptom_check_completed:
        return SafetyResult("ask", "symptom_check_required",
                            "请先完成今日不适情况确认，再查看训练建议。")

    # 肯定或无法判断均不让模型生成训练建议；症状选项由专业人士审阅。
    if today.acute_symptom_status in {"yes", "unsure"}:
        return SafetyResult("stop", "acute_symptom",
                            "本次训练建议已停止。请及时寻求医疗评估；系统不提供诊断。")

    # 渐进状态规则须启用、版本化并经专业审阅；趋势提示不是诊断。
    if reviewed_rules.trend_rules_enabled and recent.matches_reviewed_trend_rule():
        return SafetyResult("progressive_notice", "trend_rule",
                            "近期记录出现持续变化，建议休息并咨询专业人士；已暂停自动加负荷。")

    return SafetyResult("continue", None, "")
```

症状筛查未完成时不返回任何训练计划。固定选项必须覆盖需求列出的胸痛、眩晕、关节剧痛，并提供“其他不适/无法判断”；自由文本匹配只作补充提示。规则命中后不经过 LLM 润色，且覆盖模型生成和缓存建议。

> **阈值治理**：任何基于静息心率或训练表现的趋势规则，须经专业审阅、版本记录和离线用例验证后方可启用。没有审阅结论时，系统只展示用户记录，不自动将趋势转成诊疗建议。
### 14.2 多信号决策（缺失不等于正常）

```python
# backend/app/decision/vote.py
@dataclass
class Vote:
    sleep_low: bool | None       # None = 缺失/无效，不投票
    hr_high: bool | None         # 仅有质量可比的有效基线时计算
    rpe_high: bool | None        # 昨日有效训练日志的 RPE
    feel_bad: bool | None        # 用户当天主动反馈
    acwr_high: bool | None       # 仅数据充分且候选规则已审阅时计算

def decide(v: Vote) -> tuple[str, list[str]]:
    # 经审阅且数据完整的 ACWR 候选上限可单独给出负荷提醒。
    if v.acwr_high is True:
        return "downgrade", ["candidate_load_limit"]

    valid_signals = [v.sleep_low, v.hr_high, v.rpe_high, v.feel_bad]
    if sum(value is not None for value in valid_signals) < 2:
        return "insufficient_data", ["too_few_valid_signals"]

    reasons = []
    weak = 0
    for value, reason in [
        (v.sleep_low, "sleep_below_personal_baseline"),
        (v.hr_high, "resting_hr_trend"),
        (v.rpe_high, "yesterday_rpe_high"),
        (v.feel_bad, "subjective_fatigue"),
    ]:
        if value is True:
            reasons.append(reason)
            weak += 1

    if weak >= 2:
        return "downgrade", reasons
    if weak == 1:
        return "soft_downgrade", reasons
    return "normal", reasons
```

只有有效信号参与投票；阈值存入带版本、来源、校准日期和审阅人的规则配置。`insufficient_data` 不得被映射成绿灯或“身体状态良好”。

### 14.4 每日调整接口

```python
# backend/app/api/today.py
@router.get("/today")
async def today(user = Depends(auth)):
    hold = await load_active_safety_hold(user.id)
    if hold:
        await invalidate_today_cache(user.id)
        return safety_hold_response(hold)  # 跨日仍暂停，不给训练条目

    signals = await load_signals(user.id)  # 手动记录优先；只读有效且未过期的数据
    safety = check_safety(signals.today, signals.recent, reviewed_rules=load_rules())

    if safety.action in {"ask", "stop", "progressive_notice"}:
        if safety.action in {"stop", "progressive_notice"}:
            await persist_safety_hold(user.id, safety)  # 与安全事件在同一事务写入
        await invalidate_today_cache(user.id)  # 新筛查/安全状态优先于预生成建议
        return {
            "level": safety.action,
            "plan_items": [],
            "reasons": [safety.reason_code] if safety.reason_code else [],
            "message": safety.message,
            "rollback_token": None,
        }

    level, reasons = decide(signals.vote)
    if level == "insufficient_data":
        return {
            "level": level,
            "plan_items": [],
            "reasons": reasons,
            "message": "当前状态信息不足，补充训练记录或主观感受后再生成调整建议。",
            "rollback_token": None,
        }

    text = render_explanation_template(reasons, signals.public_explanation_fields)

    items = await build_items(user.id, signals, level)
    if level in {"downgrade", "soft_downgrade"}:
        await emit("downgrade_event", user.id, reasons)
    return {"level": color(level), "plan_items": items, "reasons": reasons,
            "explanation": text, "rollback_token": new_token(user.id)}
```

安全筛查与 `safety_hold` 查询始终先于缓存和模板解释；急性症状或已启用的持续异常规则命中时，在同一事务内创建/保留暂停状态，并使旧的今日建议缓存失效。`safety_hold` 存在期间，即使跨日、重新登录或命中旧缓存，也不生成训练条目或自动增加负荷。通过 `POST /api/safety-resolution` 记录恢复确认后才解除暂停；急性症状必须确认已恢复且已获得专业意见，持续异常提示需确认已恢复；后者不要求专业意见字段。该确认是用户自述，不代表医疗评估。`ask`、`stop` 与 `progressive_notice` 均不返回当日训练条目；任何生成式组件都不能恢复被拦截的建议。

### 14.5 ACWR 计算（仅在完整日记录窗口上）

ACWR 的查询不应只对有训练的日期做 `ROWS BETWEEN`：那样窗口表示的是 28 条训练记录，不是 28 个日历日。每日状态必须区分“确认休息（日负荷为 0）”与“没有记录（未知）”；仅当近 28 个日历日均有有效记录且训练时长/RPE 有效时，才计算并保存 ACWR，否则结果为 `NULL`。

```sql
-- 示意步骤，需由迁移与查询实现补全：
-- 1. 生成用户近 28 个日历日的日期序列；
-- 2. LEFT JOIN 每日训练记录与“已确认休息/未记录”状态；
-- 3. 汇总有效训练的 session_load = RPE × 分钟数；确认休息记 0，未记录记 NULL；
-- 4. 仅在完整 28 日窗口上计算 acute_7d / (过去 28 日平均日负荷 × 7)。
-- 缺任一日的记录状态时，acwr = NULL；不得把缺失补成零。
```

ACWR 是可选的派生观察字段；没有有效完整窗口时不投票、不显示“超标”，也不影响基于手动 RPE/主观感受的基础流程。

### 15.3 安全评测用例边界

安全规则至少覆盖以下测试类别：

- 结构化筛查中胸痛/胸闷、眩晕/晕厥、严重关节痛、“其他不适”和“无法判断” → 不生成训练计划；
- 未完成今日筛查 → 先要求完成筛查，不展示今日训练建议；
- 安全红线创建的暂停状态跨日期持久化；新设备会话、旧缓存、周计划、回退和模型解释都不能重新显示训练建议或增加负荷；`safety_hold` 有外键级联删除；
- 急性症状需用户确认已获得专业意见且已恢复，持续异常提示需确认已恢复；解除时间留痕，用户确认属于自述，不视为医疗验证；
- 缺少睡眠、心率或历史数据 → 该项不投票，并明确显示缺失；全部关键状态输入均缺失时返回“信息不足”；
- 持续异常趋势规则只在有足够有效数据、专业审阅启用后测试；未启用时确认不会误触发。

固定测试集上的“全部通过”是发布前的必要条件；上线后仍需收集误报、漏报和用户不适反馈，及时暂停有问题的规则版本。

### 15.4 ACWR 的适用边界与受伤事件观察

需求文档 3.8 要求观察 ACWR 超标次数，但 ACWR 在本项目中只是**代理观察指标**，不是经验证的个人伤病预测器，也不能用单一阈值证明安全。阶段一刚开始时没有 28 天历史，不能计算；用户漏记训练时也不能假设负荷为零。只有明确算法、有效记录门槛、对照组和候选阈值并完成专业审阅后，才在试点报告中比较趋势。

受伤事件是低频且依赖主动上报的结果指标。小规模试点只记录事件并回溯近期训练与建议，不宣称“受伤不增加”或“ACWR 改善意味着受伤风险下降”。如发生疑似与系统建议相关的不适/受伤，暂停相关建议规则并进行人工复盘。


## 16. 风险清单

### 16.1 合规 / 安全类

| 风险 | 表现 | 对策 |
| :--- | :--- | :--- |
| **健康数据未经单独同意** | 敏感健康信息未经单独授权即收集 | 独立授权、版本留痕；撤回即停止新增采集；未完成授权与删除验证不得开始内测 |
| **误以为免责声明能免责** | 因建议不当造成侵权仍需担责（3.7 原话） | 不把免责声明当豁免依据；产品上"少给结论多给依据"；MVP 不公开发布 |
| 症状漏报或安全筛查绕过 | 自由文本关键词未命中、缓存/周计划重新展示训练建议 | 主动结构化筛查；未回答/不确定时停止生成；停止状态覆盖 LLM、计划和缓存；已审阅安全用例全过 |
| 趋势规则误报或误当诊断 | 用户手动数据噪声大、缺失或未经审阅 | 趋势数据不足时不触发；阈值审阅、版本化；未审阅前关闭趋势规则，触发后仅作保守提示 |
| 越界成医疗诊断 | 回答暗示病因或保证不会受伤 | 禁止病因推断/疗效保证；固定模板并纳入人工审阅与评测 |
| 定位被误解为教练替代 | 用户按 AI 建议放弃原有教练计划 | 明确"训练助理"定位；教练批注优先级高于 AI（9.6） |
| 健康数据删除不彻底 | 主库已删但缓存、队列、备份仍保留 | 删除覆盖主库（含 `safety_hold`）及在线副本；备份披露保留期限并到期清除；不必要不存原始回包 |
| 平台条款变化 | 可穿戴数据获取方式被限制 | 阶段二接入前重新核对平台条款（3.13 假设 1、3.15） |

### 16.2 工程类

| 风险 | 表现 | 对策 |
| :--- | :--- | :--- |
| **健康字段被发往外部模型** | 周计划请求含伤病史或恢复数据，超出用户预期 | 每日解释不调用 LLM；周计划云模型单独评估、逐项授权与最小化；无授权则关闭云路径 |
| **手动记录缺失或录入错误** | 睡眠/心率/RPE 未填或日期、单位填错 | 未知值不当作正常值；表单校验日期/范围；卡片展示来源和缺失提示；数据不足时不给确定性结论 |
| 平台能力或权限与预期不符 | 设备、系统版本、平台授权或 API 变化 | 可穿戴探测独立于 MVP；逐设备记录实测条件；无资质/设备则标注未验证，不承诺字段 |
| MVP 恢复字段不足 | 用户未填睡眠/静息心率 | 按阶段一手动输入范围运行；未填字段标未知，不阻塞基础计划，也不暗示具备自动设备数据 |
| 规则阈值缺乏依据 | 个体差异导致误报/漏报 | 阈值需专业审阅、预设规则版本并用数据回顾；不以规则配置可调替代有效性验证 |
| 就低不就高导致过度保守 | 用户觉得"总是让我减量"，执行率下降 | 解释必须具体（9.3）；一键回退给控制权（9.4）；观察接受率（3.8 ≥ 70%） |
| 用户不接受降负荷 | 3.13 假设 4 的风险 | 同上；接受率作为持续观测指标 |
| RPE 记录率低 | 3.13 假设 2，主观信号消失 | 记录入口极简（一次点选）；记录率作为观测指标 |
| 用户所在时区或日期录入错误 | 跨时区日切错位、训练记入错误日期 | 保存用户时区和录入时间；日期可由用户确认，测试日切边界 |
| 平台重复回包 | 同一天数据写入两次 | 主键 `(user_id, day, source)` + upsert |
| 批任务打爆数据库 | 凌晨批量同时跑，在线请求变慢 | 分片 + 错峰 + 独立连接池（12.2 / 12.3） |
| 周计划模型不可用 | 外部模型超时或用户未授权 | 未授权走本地规则模板；超时明确告知，安全筛查与每日建议继续按本地规则运行 |
| 周计划越过安全结论 | 云模型生成与规则/禁忌冲突 | 日常结论由本地规则生成；周计划模型输出需再过规则、禁忌和结构校验（9.3 / 14.2） |
| 教练批注被模型覆盖 | 专业人士意见失效 | 批注在 `generate` 之前注入，作为硬约束（9.6 / 14.3） |
| 基线周被跳过 | 新用户直接上激进计划 | `baseline_ready` 门禁；冷启动用例断言"无激进计划" |
| 后续健康平台接入延期 | 需要原生桥接、平台审核或 API 替换 | 阶段一不依赖平台接入；完成单独可行性探测后再立项 |


## 17. 下一步

建议按以下顺序推进：

1. **先落实 M0 的启动条件**：确定仅邀请制的成年试点用户、隐私授权与删除说明负责人、健康安全规则审阅人，以及试点中止和问题上报联系人。

2. **做 M1 阶段一输入验证**：在桌面和移动浏览器验证手动训练/RPE/主观感受/睡眠/静息心率录入和数据缺失展示。HealthKit / Android 平台探测作为独立后续任务，条件不齐时明确记为未验证。

3. **先固化评测集与规则审阅流程，再实现安全决策层**：覆盖结构化症状筛查、筛查未完成、含糊输入、缺失/过期数据、停止态缓存覆盖。未审阅的连续心率或 ACWR 阈值先保持关闭。

4. **端到端打通手动数据 MVP**：建档与同意 → 生成周计划 → 每日安全筛查与调整 → 训练后记录 → 展示原因与回退 → 撤回授权/删除数据。

5. **预注册小范围试点口径**：若目标是验证需求 3.8 的执行率提升，先确定对照方案并准备两组各至少 30 人、4 周记录的条件；达不到时只做可用性与可行性报告，不作效果结论。
